一、專案背景

校園師生用餐需求集中於午餐時段，傳統現金結帳方式效率低、易產生排隊壅塞；同時廚房端難以即時掌握當日備餐數量，常造成「備太多浪費」或「備太少售罄」的兩難。為提升用餐體驗、降低營運成本，本案規劃導入一套整合「線上預訂、電子錢包、廚房備餐、取餐核銷」的校園 POS 系統。

本系統聚焦三大目標：使用者端的便利性、廚房端的可控性，以及行政端的可追溯性，並以 Kitchen.txt 所列之資料模型為基礎，為功能落地提供穩固結構。

二、系統目標

  • 提供學生與教師線上預訂套餐、繳付訂金、查詢餘額的完整自助流程。
  • 讓廚房可預先設定每日供應數量、開放與關閉預訂時間，避免食材浪費。
  • 讓行政端能即時為錢包進行儲值、扣款、退款，並完整保留交易紀錄供稽核。
  • 透過取餐核銷機制，掌握每筆訂單的預計取餐與實際取餐情形，降低逾時未取的損失。
  • 資料模型可擴充至未來「多攤位」、「多時段」（早午晚餐）與「節慶活動套餐」等情境。

三、系統角色與權限

本系統共分四類使用者，所有人皆繼承於 USERS 主檔，並以子表延伸專屬欄位：

角色代表資料表主要權限

四、核心功能模組

4.1 會員與錢包模組

Phase 1–2 簡化方案：付款暫以現金 / 支票方式處理，由 Admin 手動於後台調整訂金與餘額，系統僅作為金流紀錄之載具。完整自動付款（線上儲值、第三方金流串接、自動扣款）將於 Phase 3–4 推出。
  • 註冊 / 登入：以手機號為帳號、密碼以 hash 儲存（Password_Hash）。
  • 錢包（Phase 1–2 手動模式）：每位使用者建立 Wallet，Balance 由 Admin 收到現金或支票後手動入賬。
  • 訂金 / 尾款（Phase 1–2 手動模式）：使用者下單後產生待付金額，Admin 確認收款後於後台手動標記 Order_Status 為 Deposit_Paid / Fully_Paid。
  • 交易明細：Admin 每筆手動調整皆寫入 Wallet_Transactions（含 Admin_ID、TYPE、Description、Created_At），保留完整稽核軌跡。
  • Phase 3–4 升級：線上儲值、Linepay / Stripe / 校園卡串接、自動扣款、自助退款。

4.2 菜單與庫存模組

  • 菜單 (Menus) 為「主菜 + 飲品」之組合套餐，由廚房 (Kitchen_Users) 維護。
  • 每日設定 Initial_Stock 與 Available_Stock，售完自動標記 Is_Sold_Out。
  • 以 Booking_Open（如 18:00）與 Booking_Close（如 11:00）控制預訂時間窗。
  • Meal_Type 支援週一至週六不同供應計畫，方便週間排程。

4.3 訂單與訂金模組

  • 使用者建立訂單 (Orders) 後，依品項建立 Order_Items。
  • 當 Total_Qty ≥ 4 時，系統自動帶入 Deposit_Amt = 50（訂金機制）。
  • Order_Status 共四階段：Pending_Pay → Deposit_Paid → Fully_Paid → Complete。
  • Phase 1–2：Admin 收取現金 / 支票後，於後台手動點按「已收訂金 / 已收尾款」更新狀態。
  • Special_Note 欄位可記錄敏感需求（如「不要海鮮」、「少油」、「走甜」）。

4.4 取餐核銷模組

  • 每筆 Order_Item 對應一筆 Meal_Pickups，核銷以手機末四碼比對 (Method)。
  • Expected_Time 為預計取餐時間，Actual_Time 為實際取餐時間（未到則為 NULL）。
  • Admin_Notified 為通知旗標，逾時未取時提醒行政與廚房處理。

五、主要業務流程

5.1 預訂與付款流程

  1. 使用者於 Booking_Open 後瀏覽當日菜單，選擇套餐並加入訂單。
  2. 系統依 Total_Qty 計算是否需付訂金（≥4 套餐則 Deposit_Amt = 50）。
  3. 使用者由電子錢包扣款 → 寫入 Wallet_Transactions（TYPE=Deduct）。
  4. 訂單狀態更新為 Deposit_Paid 或 Fully_Paid。
  5. Booking_Close 後，廚房依 Order_Items 統計備餐。

5.2 取餐核銷流程

  1. 使用者於 Expected_Time 抵達取餐窗口。
  2. 行政以手機末四碼於 POS 介面查詢未取訂單。
  3. 完成核銷後，Meal_Pickups.Actual_Time 紀錄當下時間。
  4. Order_Items.Pickup_Status 更新為 Picked_Up；全部完成後，Order_Status → Complete。

5.3 退款與例外處理

  1. 逾時未取：系統將 Admin_Notified 設為 1，由行政決定是否退訂金或全額退款。
  2. 廚房沽清：自動將 Menus.Is_Sold_Out 設為 1，並對已下單但未供餐者退款。
  3. 所有退款動作皆寫入 Wallet_Transactions（TYPE=Refund），便於月結對帳。

十一、預期效益

  • 用餐效率提升：預估排隊時間由 8 分鐘降至 2 分鐘以內。
  • 食材浪費下降：透過預訂制與 Initial_Stock 預估，預計可降低 30% 廚餘。
  • 營運可視化：行政可即時查詢每日銷售、退款與逾時未取數據。
  • 數位化校園：建立校園統一錢包雛形，未來可擴充至福利社、影印、活動報名等場域。

十三、結論

本提案以 Kitchen.txt 之資料模型為基礎，搭配上述功能模組、業務流程與技術架構，可有效解決現行校園餐廳之效率與管理痛點。建議優先啟動 Phase 1 – 2（3 週，HKD $245,000），以「現金 / 支票 + Admin 手動入賬」模式快速上線，待流程穩定、使用者習慣養成後，再推進 Phase 3 – 4 之自動金流與優化。

此分階段策略可大幅降低初期投入風險、加快上線速度，並讓業主有時間觀察實際使用情形再決定是否續推完整版。

如蒙採用，後續將提交 《系統規格書》、《資料庫實體設計 (PostgreSQL DDL)》、《介面原型 (Figma)》 三份子文件，以利專案啟動。
