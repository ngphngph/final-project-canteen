DEVELOPMENT DIRECTION

系統開發方向 — 架構說明

校園餐廳 POS 系統 · 技術策略文件 · v1.2 · 2026-06-03
本系統採 Microservice（微服務）架構，將後端拆分為 5 大獨立服務，前端整合為 1 套統一介面。 Wallet 獨立以保留未來 SaaS 銷售彈性；Cart 與 Order 合併為 Checkout Service，以確保「加入購物車 → 下單 → 訂金」流程之資料一致性。 開發團隊以 Agile Scrum 流程運作，每兩週一個 Sprint 並進行 Review，確保進度透明、需求可調整。

二之一、關鍵設計決策

議題決策理由
Wallet 是否獨立？ ✅ 獨立服務 保留未來作為 SaaS 銷售予其他學校、福利社、影印站之彈性；錢包之查詢、儲值、退款本身即為獨立業務領域
Cart 是否獨立？ ❌ 併入 Checkout Cart 與 Order 屬於同一條結帳鏈、共用同一筆資料生命週期；合併可確保資料一致性，避免分散式交易（Saga）之開發成本
Wallet 與 Order 是否合併？ ❌ 不合併 合併會綁死錢包與訂單，無法獨立銷售；改以 Saga Pattern 處理「扣款 + 建單」之最終一致性（補償機制：扣款失敗則訂單回滾、建單失敗則自動退款）

二之二、Nginx — 系統的「交通警察」

Nginx 是擺在 5 個 Java 微服務之前的反向代理（Reverse Proxy）。前端瀏覽器只認識一條大馬路 http://54.82.49.xxx（Port 80），而 Nginx 站在 Port 80 攔截所有流量，依路徑分流到正確的後端服務。

部署方式：
  • 有 Docker：使用官方 nginx image，已內置，掛載 nginx.conf 即可。
  • 無 Docker：在 EC2 直接安裝：sudo apt install nginx → nano /etc/nginx/nginx.conf → sudo nginx -t → sudo systemctl restart nginx

四大職責

職責說明
① 指揮交通（反向代理） 前端只認 http://54.82.49.xxx 一條馬路，Nginx 看到 URL 路徑就分流：
  • /api/identity/ 👉 Identity Service（Port 8080）
  • /api/wallet/  👉 Wallet Service（Port 8081）
  • /api/menu/   👉 Menu Service（Port 8082）
  • /api/checkout/ 👉 Checkout Service（Port 8084）
  • /api/pickup/  👉 Pickup Service（Port 8085）
② 隱藏隱私（安全性） 如果不用 Nginx，就必須把 AWS 防火牆的 Port 8080~8085 通通暴露在網際網路上，讓駭客直接攻擊 Java 程式或資料庫。 用了 Nginx，對外只開放 Port 80 / 443，內部 Java 服務全部在防火牆後面，無法被外人直接戳。
③ 抗震防崩潰（隔離故障） 5 個 Java 服務有時可能因連不到資料庫而 Restarting。Nginx 會偵測下游節點狀態，單一服務崩潰時，其他路徑仍可正常運作（例如 Wallet 掛了，使用者仍可瀏覽菜單），亦可設定 backup 節點自動接手。
④ 解決 CORS（跨域問題終結者） 前後端分離時，瀏覽器會因安全機制鎖死「網頁在 A 網址、API 在 B 網址」之請求。 用了 Nginx，前端與所有 API 都走同一個域名（同一條大馬路），瀏覽器視為 same-origin，CORS 問題自然消失。

nginx.conf 路由片段（範例）

upstream identity_service { server 127.0.0.1:8080; }
upstream wallet_service   { server 127.0.0.1:8081; }
upstream menu_service     { server 127.0.0.1:8082; }
upstream checkout_service { server 127.0.0.1:8084; }
upstream pickup_service   { server 127.0.0.1:8085; }

server {
    listen 80;
    server_name 54.82.49.xxx;

    location / {                                   # 前端 React 靜態檔
        root /usr/share/nginx/html;
        try_files $uri $uri/ /index.html;
    }

    location /api/identity/  { proxy_pass http://identity_service/; }
    location /api/wallet/    { proxy_pass http://wallet_service/; }
    location /api/menu/      { proxy_pass http://menu_service/; }
    location /api/checkout/  { proxy_pass http://checkout_service/; }
    location /api/pickup/    { proxy_pass http://pickup_service/; }
}

※ 完整檔案見 nginx.conf（已含日誌、Gzip、健康檢查、Header 傳遞等完整設定）。

三、為什麼採 Microservice？

優勢說明 / 對本案的意義
獨立部署單一服務改版不影響其他模組，例如菜單服務更新不會中斷取餐核銷。
獨立擴展午餐尖峰時段，可單獨擴充 Order / Pickup 服務之資源，省成本。
獨立銷售Wallet Service 可獨立銷售給其他校園、福利社或社區商店；Menu + Order 亦可包裝為小型餐廳 POS 方案。
技術選擇彈性各服務可使用最合適之技術堆疊，未來重寫某一服務也不影響全局。
故障隔離單一服務出問題時，其他模組仍可運作（例如錢包暫停，菜單仍可瀏覽）。
團隊分工清晰Scrum 團隊可依服務分工（A 組負責 Identity + Wallet、B 組負責 Menu + Order + Pickup）。

六、Agile Scrum 開發流程

專案以 2 週為一個 Sprint，6 週共 3 個 Sprint 完成 Phase 1–2。團隊角色與儀式如下：

6.3 Sprint 安排（對應 Phase 1–2）

6.4 開發工具與管理

  • 需求 / Backlog：Jira 或 Linear，依優先度排序
  • 程式碼：GitHub，每個微服務一個 Repo（Mono-repo 亦可）
  • Code Review：所有 PR 至少 1 人 Review 才能合併
  • Definition of Done：程式完成 + 單元測試通過 + Code Review 通過 + 部署至 Staging 可運行
  • 每週客戶 Demo：於 Sprint Review 中向業主展示進度，及時調整方向

七、結語

本系統以 Microservice + Agile Scrum 為核心策略，兼顧「短期快速上線」與「長期靈活擴充」兩大目標：

  • 短期：3 週內以 6 人團隊完成 Phase 1–2，依「現金 / 支票模式」上線運行。
  • 中期：Phase 3–4 加入金流自動化、推播通知，達成完整自動化。
  • 長期：每個服務皆可獨立銷售予其他學校或場域，創造延伸商業價值。

透過每兩週 Sprint Review，業主可全程參與並調整需求，確保最終成果貼近實際營運需要。
